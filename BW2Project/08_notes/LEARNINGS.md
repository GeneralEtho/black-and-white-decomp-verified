# Learnings: proven, generalisable lessons only (curated by Fable)

Format per entry: `### slug` / `Rule:` / `Evidence:` (which card, which check run). Nothing goes here on a hunch.

### mac-binary-is-base-game
Rule: the Mac BW2 1.0.1 symbols describe the base game; BotG-only code (49 natives, classes like EnemyGod, Abbatoir) has no Mac counterpart and must be named from RTTI + the BotG native table.
Evidence: fresh-eyes review 2026-10-22, native-name census of all three binaries.

### native-table-is-bw1-layout
Rule: `{fn, stackIn, stackOut, unknown, char name[128]}`, 144 bytes per entry, in `.data` on Windows (v1.42: 0x171e540) and `__data` on Mac (0x14e1450); index i on one side is index i on the other for the base game.
Evidence: three entries resolved by hand to GScript::* symbols, 2026-10-22.

### a-byte-sweep-is-not-disassembly
Rule: never report an address claim (a call, a jump, a hook) from a linear pattern scan over code bytes; an E8 or E9 inside an operand looks like a call. Decode with a real disassembler (Ghidra or capstone) before the claim enters FINDINGS, and keep a known-false-positive canary in any scan tool.
Evidence: the "call 0x242bbc6 from 0x4142c9" claim of 2026-10-22, refuted by crazy hacker man and verified against the vault bytes (`80 0D E8 F8 78 01 02`).

### fan-patch-is-inline-plus-crack-plumbing
Rule: in the 1.42 exe, the fan edits are ten inline byte runs in `.text` (plus two strings and one data value); `.name0`, `.name1` and the 28 `stxt774` jumps are the crack's SafeDisc-SDK stand-in; 26 function bodies are int3 fill in every decrypted v1.2 and must be marked MISSING. Static diff against a vanilla reference is the only way to list fan edits; a memory dump cannot see them.
Evidence: FINDINGS.md "the fan exe versus vanilla", 2026-10-22.
### compare-counts-the-same-way
Rule: never compare two numbers produced by two different scripts (the 1,366 vs 2,840 RTTI mistake). One script, both inputs, same run.
Evidence: fresh-eyes review 2026-10-22.

### test-the-reviewers-reading-never-apply-it
Rule: when a reviewer names a cause from reading code ("claimed reading, to test first"), the executor measures it on the run before fixing anything; a reading that fits the symptom can still be wrong, and a fix built on it would have left the real cause in place. The card says "test first", the report says what held and what did not.
Evidence: T05F1 item 6 (DECISIONS.md "2026-10-26 (Fable, T05F1 review, C-04 update, T06 batch 1)"): the reviewer's reading of the vtable end cause (a slot target with no instruction ends the table) held for one class of five; for the other four the executor found a READ reference from an indirect call through the slot ending the table (SlotProbe.java, evidence/slot-probe.txt; capstone, cause_capstone.out in 05_work/analysis/t05f1-verification).

### a-crash-guard-is-not-an-attempt
Rule: when a one attempt test would crash on an input shape its author never saw (a class that does not pair, a missing table), a guard that turns the crash into the printed figures and a FAILS verdict may be written before the attempt; it changes no pass condition, so it is not a second attempt and not a change to the test. A guard that changes what passes is a rule change and goes to Fable first.
Evidence: T09B1 (DECISIONS.md "2026-10-29 (Fable, T09B1 sign-off, T08B1 stop rule, T12B7 fix)"): band_test.py --botg would have crashed on a missing Object (608 Mac slots against 618 BotG); the executor added the no Object guard before the one attempt, the test printed FAILS part g with its figures (b1-band-test.txt), the verifier found nothing in the code the report left out (band-mine5-run.txt), and the reviewer accepted it.

### run-the-ledger-check-before-the-first-commit
Rule: a committing session runs C-17 over the pending ledger lines before its first commit, because C-17 counts every line ever added in git history and a committed line with a wrong result word cannot be taken back out.
Evidence: two verifier lines with the word "result" went into commit 6cad125 on 2026-10-28 and keep C-17 at FAIL until T14R3 (DECISIONS.md "2026-10-28 (Fable, T06 batch 4 sign-off, license, T08 and T09)"); the Fable session of 2026-10-29 ran C-17 first and found only those two (05_work/analysis/fable-review-20261029/c17-run.txt).

### blind-test-before-naming
Rule: a name method proves itself on the functions that already carry a verified name before it names one unknown function: run blind over the verified set (their names hidden), it must agree with 95 percent or more of the names it predicts, and the predicted count is reported beside the agreement; under 95 the method never runs over the unnamed set. The verifier's holdout stays as the second measure. A rule added inside the vtable method keeps its own HOLDS before names test instead, because running the vtable method over its own names measures nothing.
Evidence: T08B1 named 1,441 functions and its holdout read 8 inconsistent of 85 readable (05_work/analysis/t08b1-verification/out/pool1-counts.txt); T08B2 named 255 and its holdout read 6 of 79 (05_work/analysis/t08b2-verification/out/step7-counts.txt); both methods could have been run over the 9,149 T06 anchors first at no cost to the holdout. DECISIONS.md "2026-10-30 (Fable, T09B2 sign-off, T08 closed, string anchors, T12B7F, mirror)", ruling 3; PLAYBOOK.md hard rules.

### a-generated-output-is-not-a-touched-file
Rule: a script output a card asks for (a dated run log, a cross-check output file) is listed on the card under "Generated outputs, not counted" with its path, never under Files touched, because C-16 counts every line of every Files touched path against the card's budget and a 483 line output file is not the executor's work.
Evidence: T12B7F read 658 changed lines against a budget of 200 at efab156, 483 of them ptg_crosscheck.2026-10-29.out.txt (05_work/analysis/fable-review-20261030/numstat-budgets.txt, c16-run.txt); T09B2 listed its tables and run logs under a generated outputs line and read 906 against 900 for ledger lines alone. DECISIONS.md "2026-10-30 (Fable, T09B2 sign-off, T08 closed, string anchors, T12B7F, mirror)", Budgets.

### a-run-that-measured-nothing-is-not-an-attempt
Rule: when a one attempt test is run over an input that lacks the field the test reads (a stale generated file, a cache made before the tool gained a key), every class fails at its first lookup and no condition of the rule is evaluated; that run is not the attempt. The executor keeps its output, discloses it on the card and in the ledger, remakes the input with the same tool, changes no line of the test and runs once more; the verifier reproduces the void run from the input (strip the field, run the test unchanged, compare line for line) before the second run counts. A run whose output shows the rule's conditions being evaluated is the attempt, pass or fail.
Evidence: T06B5 rule 18 (DECISIONS.md "2026-10-31 (Fable, T08C1 and T06B5 sign-off, combined 1.42 file, T08C2, T06B6)"): the first run read a mac_vtables.json made before mac_vtables.py gained secondary_groups and printed 12 "does not hold" lines at the first lookup (05_work/analysis/t06/run-logs/b5-rule18-test-void.txt); the verifier stripped the field from the batch's json and rule18.py unchanged printed the same 12 lines (05_work/analysis/t06b5-verification/out/rule18-nogroups-run.txt); the second run evaluated the rule and FAILed 7 of 12 on its wording, which the ruling then amended for T06B6.

### a-position-independent-binary-references-through-its-base
Rule: on a position independent binary (the Mac BW2 build), a reference to a data address is almost never an immediate operand; it is "call next; pop reg" followed by [reg + displacement], and the referenced address is the pop's own address plus the displacement. A reader that looks for immediates finds nothing and the method cannot run; the PIC base reading is the definition of a reference there, written into the card before the run. A stricter reading that follows the base register through calls, jumps and returns is the check on it (it finds more references and must never reject one the simple reading accepted at a pair string without the row being read).
Evidence: T08C1 (DECISIONS.md "2026-10-31 (Fable, T08C1 and T06B5 sign-off, combined 1.42 file, T08C2, T06B6)"): 17 immediates, 0 absolute addresses and 35,168 PIC base references of 35,185 (mac_refs.py, 05_work/analysis/t08/run-logs/c1-references.txt); the verifier's tracking reading finds 1,364 more and misses 7, touching the pair set at one string whose row the holdout read as consistent (05_work/analysis/t08c1-verification/macref_judgement.txt, marks1.tsv row 84).

### a-shared-tools-folder-inflates-every-card-that-lists-it
Rule: a card that lists a shared tools folder under Files touched is charged by C-16 for every later card's files in that folder until the check is revised; the overrun of a closed card is excused by a Fable OVER-BUDGET line in the ruling 1c form naming the later card, never by changing the budget, and a new card that reuses a folder says in its why line what is new and what exists.
Evidence: T09B1 at efab156 (1505 against 900, T09B2's six scripts; DECISIONS.md 2026-10-30), T08B1 and T08B2 at 1cc2cd7 (2324 against 1500 and 1626 against 600, T08C1's 1,087 tool lines; 05_work/analysis/fable-review-20261031/c16-run.txt, numstat-budgets.txt); T14R3 item 12 holds the question.

### a-gap-function-body-can-hide-a-block
Rule: a reference reader that walks Ghidra's body of a census function found by the gap sweep can miss a block the function really holds, so a method built on that export is conservative (it loses names and never adds wrong ones); the check on it is the verifier's own capstone pass over every range of the function (extent, not size), and a name found by one reader only is recorded as a known limit and never emitted by a ruling. A later method that wants those rows reads every range with capstone as its definition of a PC reference and runs blind first.
Evidence: T08C2 (DECISIONS.md "2026-11-01 (Fable, T08C2 and T06B6 sign-off, two methods closed on yield, T08C3)"): the verifier's capstone view found the two pair string references of 0xa74990 (found_by gap, size 344, extent 559) at 0xa74ac9 and 0xa74aee, which the Ghidra body lacks, one name more than the batch (05_work/analysis/t08c2-verification/run-logs/recount-pair-mine-run.txt); 5,539 census functions have extent not equal to size and 142 strings differ in function sets between the two views (cmp-refs-run.txt).

### a-diff-accounting-is-part-of-the-check
Rule: the allowance list of a batch's diff script (which rows may change and how) is part of what passes, written for the shapes its author had seen; when a later batch meets a legal shape the list does not name, the executor leaves the tables as the rules build them and the FAIL line as printed, changes neither the accounting nor a row by hand, and reports the row; the reviewer rules on the shape and the next executor teaches the script the case. Widening the list to make the run pass is a change to what passes and goes to Fable first.
Evidence: T06B6 (DECISIONS.md "2026-11-01 (Fable, T08C2 and T06B6 sign-off, two methods closed on yield, T08C3)"): 0x4bedd0 went from "claimed, T06B1" to "folded, 2 names" through a rule 11 fold of byte identical Mac bodies (capstone, 05_work/analysis/t06b6-verification/out/bodies6-run.txt), which the card allowed and batch 5's grown_by accounting counted under "any other reason", so diff_batch1.py --b5 printed DIFF: FAIL (05_work/analysis/t06/run-logs/b6-diff-b5.txt); the executor left it, the verifier reproduced it, and the ruling amended the doc sentence.

### a-vtable-store-is-not-a-constructor
Rule: a function that stores a class's primary vftable address is not thereby its constructor or destructor: factories (Create functions), posting functions and inlined constructions of a member or an interface store the same address, and the order of stores and base calls cannot tell them apart. A vtable store may serve as evidence beside another signal; alone it names nothing. The companion lesson: a blind set drawn from a population the unnamed set does not resemble (here the 541 virtual destructors and constructors the vtable method had named at vtable slots, against the non virtual constructors and factories the signal ran over) proves little even at 100 percent, and a blind test that predicts under 100 rows is reported as proving little and leaves the weight on the holdout.
Evidence: T08C3 signal (a) (DECISIONS.md "2026-11-02 (Fable, T08C3 rulings, the holdout rule, the last 1.42 signal, the pivot)", ruling 1): blind test 36 of 541 at 100.00 percent (05_work/analysis/t08/run-logs/c3-blind-store.txt), then 54 names of which the verifier read 5 inconsistent, 9.26 percent, three Create or posting functions and two inlined constructions (05_work/analysis/t08c3-verification/holdout-marks-a.tsv), and all 12 conflict rows fitting neither name (holdout-marks-conf.tsv); the 54 rows withheld (05_work/analysis/fable-review-20261102/withhold-t08c3-run.txt).

### the-holdout-is-the-verifiers-own-reading
Rule: a holdout row counts only when the verifier itself read the decompiled body and wrote the sentence and the mark; a row read by a delegated agent, a helper, or from names and shape alone is not read, and a holdout holding such rows has not been run; a verifier that cannot read every row says so and the batch waits. A helper working from the verifier's own dossier is not a second reader, and a mark made from names and shape is the batch's evidence read back; the verifier's spot check of a helper's rows does not make them read rows. Disclosing the delegation, as the T08C3 verifier did, is what lets the ruling be made cleanly; the fix is a fresh read of every row, nothing else re-done.
Evidence: T08C3 signal (b) (DECISIONS.md "2026-11-02 (Fable, T08C3 rulings, the holdout rule, the last 1.42 signal, the pivot)", ruling 2): 80 of 80 rows marked consistent by a Sonnet helper agent from names and shape, 5 re-read by the verifier (05_work/analysis/t08c3-verification/holdout-b-agent-notes.txt, holdout-b-spotcheck.txt; the verification report 7.2 and 12); the 80 rows stay claimed and unverified under T08C3V2-sets-holdout.md. PLAYBOOK.md hard rules.

### a-single-leftover-call-is-where-compilers-differ
Rule: a pairing rule whose reach rests on lists with one direct call and nothing else (a named part of 0) is measuring the one place the two compilers are least alike: one side inlines a one call helper that the other side calls, or reaches the counterpart by a tail jump that convention C1 leaves out, so the one callee left over on the PC is not the one left over on the Mac. Report how many candidate ties have a named part of 0 before the blind test, and expect a rule that leans on them to fail it; a subset that keeps two or more agreeing named callees can pass and still name nothing when few ties have that shape. A tail jump aware call list is a change to C1 on both sides, written and blind tested first, never a patch to a failed run.
Evidence: T08C4 (DECISIONS.md "2026-11-03 (Fable, callee set accepted, T08C4 closed, the 1.42 plateau, the pivot opened)", ruling 2): 658 of 731 round 1 ties had a named part of 0 (singleton8.py, 05_work/analysis/t08/run-logs/c4-anchors.txt; the verifier's recount4.py agrees); the blind test predicted 59 of 10,850 and agreed on 51, 86.44 percent, with 40 of 45 right at part 0, 4 of 7 at part 1 and 7 of 7 at part 2 or more (blind_singleton.py, c4-blind.txt, 05_work/analysis/t08/c4/blind-test.tsv); the verifier's 30 seeds read 84.00 to 94.44 percent with the same 11 functions wrong wherever predicted (seeds4.py, 05_work/analysis/t08c4-verification/blind-seeds-run.txt), and its capstone read of the 8 misses found the Mac anchor reaching the true counterpart by a tail jmp in 6 of 8 and by a call in 0 of 8 (mech8.py, mech8-run.txt).

### a-blind-test-proves-the-rows-it-can-sample
Rule: a blind test proves a name method on the rows it can sample, which are the functions that already carry a verified name, and those rows need not look like the rows the method then names; the report says how the blind set resembles the named rows (source table, body size, kind of function), the verifier's holdout is drawn from the rows actually named, and where the blind set does not resemble them the weight of the verdict rests on the holdout. A method that passes a blind test over small vtable bodies has not been shown to work on large non vtable bodies until a holdout drawn from those has been read.
Evidence: T09B3 (DECISIONS.md "2026-11-04 (Fable, T09B3 and T13C1 sign-off, the BotG number, his source names, PUBLISH7, T10B1)", ruling 1): every one of the 2,384 blind rows took its 1.42 name from the T06 vtable table, median body 47 bytes, 15.8 percent short, while 1,021 of the 1,105 names carried came from the T08 tables, median body 308 bytes, 0.8 percent short (v3_blind.py RESEMBLANCE lines, 05_work/analysis/t09b3-verification/out/v3-blind-run.txt); the holdout of 100 was drawn from the 1,105 named rows, 85 of them string method rows, read by the verifier itself against both builds' bodies, 0 inconsistent (v6_draw.py, v8_counts.py, marks.tsv), so the batch stood on the holdout and the blind test stood as the gate it was. PLAYBOOK.md hard rules, the blind test.

### a-repeated-name-is-a-label
Rule: when names are taken from another person's table, a row by row form test (address forms, slot forms, compiler made names) is not enough: the same text stamped on many addresses is a label of a kind of function, not a reading of any one of them, and so are the thunk forms a list spelt too narrowly (j_j_sub_<hex> beside j_sub_<hex>, scalar_deleting_dtor_thunk_<name> beside scalar_deleting_dtor). Count how many rows carry each name before the reading, treat a name on 10 or more rows as a placeholder, and report the proportion that fits over the named rows apart from the labels.
Evidence: T13C2 (DECISIONS.md "2026-11-05 (Fable, T10B1 live, T13C2 read status, PUBLISH7, INTAKE4, T10B2)", ruling 3): 66 of the 1,316 outside rows carried four label forms, 4 j_j_sub_<hex>, 3 scalar_deleting_dtor_thunk_, 17 one Concurrency inventory name and 42 _cleanup (05_work/analysis/t13c2-verification/forms-finding.txt; the reviewer's label-rows-count.txt); the one miss of the verifier's 100 was one of the 17, a 27 byte static initializer (marks.tsv row 96), and the 94 named rows of the 100 all fit (05_work/analysis/fable-review-20261105/marks-split.txt).

### a-copy-of-dot-git-carries-the-credentials
Rule: a tar, bundle or zip of `.git` made to clone from in another place carries `.git/credentials` with it unless the file is excluded when the copy is made; excluding it afterwards means the token has already been written to a second file. Exclude at creation (`tar --exclude=credentials`), and when a copy was made without the exclusion, say so and empty it at once.
Evidence: the T10B1 executor and the T10B1 verifier (06_reports/2026-11-05_T10B1-loader-and-first-hook.md section 10; 06_reports/2026-11-05_T10B1-verification.md section 10) each made a tar of `.git` that held the credentials, each disclosed it, deleted the cloud copies and emptied the tar on the PC to 0 bytes (05_work/build/bw2hook/stage/repo-git.tar, 05_work/analysis/cache/t10b1v/game-git.tar; ls). PLAYBOOK.md hard rules, 2026-11-05.

### a-card-states-its-purpose-before-its-method
Rule: a card whose work runs code inside another program (a hook, a detour, an injected DLL) opens with one paragraph in plain words, before any method: what the thing is, whose machine and whose program it runs in, what it touches and what it does not, who reads its output, and what it proves. A session reading the card cold judges the work by that paragraph; a card that opens with the method ("detoured through MinHook") and leaves the purpose to be inferred invites a stop, and the stop is the session's right (AGENTS.md: stop and ask, never work around a refusal). The fix is the card, not the session: the next executor reads the purpose first, and a second stop at the same item replaces the item with a read only slice rather than pressing a third time.
Evidence: T10B2 attempt 1 (DECISIONS.md "2026-11-06 (Fable, INTAKE4 sign-off, T10B2 stop and rewrite)", ruling 3): the executor logged its start, made the entry read of 0x4d6880 (read_entry.py, 05_work/analysis/hook/run-logs/b2-body-read.txt, ENTRY READ: HOLDS) and stopped at item 3 before any hook source ("cannot continue the MinHook detour work", its LEDGER.md deferred line of 2026-11-02); the card's Goal opened with "Our code changes what the running 1.42 game executes" and named the detour before it said whose game, whose machine or what for; the card was rewritten with the purpose paragraph first and the fallback written in.

### a-tightened-form-rewrites-its-own-old-lines-once
Rule: when a check's accepted sentence form is tightened after lines in the old form were written (the C-16 OVER-BUDGET excuse, loose in ruling 1c of 2026-10-22, exact in T14R3 item 1), the lines the new form rejects are rewritten once, in bulk, by the role that wrote them (Fable for the OVER-BUDGET lines), with the original date, figures and reason kept and only the words the form needs added, and the rewrite is recorded in DECISIONS.md with the before and after count of the check; the alternative, a check that excuses the old form or an allowlist of the old cards, is never written. After that one pass a line that misses the form is its writer's own mistake, fixed by that session or the next, never in bulk again; and a form is tightened with its history run in the same package, so the writer sees the rejected lines before the package goes to the verifier.
Evidence: T14R3 (DECISIONS.md "2026-11-07 (Fable, T10B3 game test failed, T14R3 fix round, the history budget lines)", ruling 4): the package's C-16 over the real ledger at d2b2ff3 printed 15 problems, 8 of them Fable's own OVER-BUDGET lines of 2026-10-28 to 2026-11-01 missing "because" or "after the verification" or in another order (PUBLISH4, T06B2W, T06B3, T08C1, T08C2, T09B1, T09B2, T12B7F) and 2 cards with no line (T12B6, T13E1); rewritten and written by apply_budget_lines.py (05_work/analysis/fable-review-20261107/apply-budget-lines-run.txt, 12 of 12 MATCHES against the package's own regex), the same check then printed 3 problems, the known T13C1V, PUBLISH3 and T12B5F, none of them a budget (c16-package-run-before.txt, c16-package-run-after.txt).

### a-card-lists-only-what-its-executor-can-change
Rule: a card's acceptance names only things its executor is allowed to change; a third party binary pinned by hash (a loader, a vendored library) is listed as a control whose reading is recorded, never as a thing the acceptance requires clean, because an executor that meets such a line can do so only by replacing the binary or changing the files the card forbids. When a card is written against a reading ("our code raises a window"), the acceptance is written over the files the reading names, and the binaries outside our build are read first and put on the control side before the acceptance is fixed. An executor that stops on such a line has done right; the fix is the card.
Evidence: T10B3F attempt 1 (DECISIONS.md "2026-11-08 (Fable, the T10B3F stop, the bisection, T14R3F committed)", ruling 1): item 3 asked the import table of loader/dinput8.dll clean after the build, with part 10 failing on any listed name; the loader is Ultimate ASI Loader, pinned at sha256 d5a059aa467a in bw2hook.mk since T10B1, and imports MessageBoxW, SetWindowPos, SetForegroundWindow, FindWindowW and EnumWindows whatever our code does (05_work/analysis/hook/run-logs/b3f-window-calls.txt L1 to L5, objdump -p); the executor stopped at item 2 without improvising, and the ruling moved the loader to the control side and replaced the items.

### a-zero-count-is-read-at-the-caller-and-against-a-control
Rule: when a hook counts 0 while its jmp stays in place and its counter is reachable (the detour's operands relocated, the count line reading the slot the jmp lands in), the hooked function was not entered, and that is a fact about the game on that day before it is a fact about the hook. The next reads are what gates the call inside the game (the caller chain, with a disassembler) and what changed on the machine, and the first test is the last build that counted, rebuilt byte equal and run again on the same day as a control beside the build in question; a fix written before that pair is read is the reading applied, not tested. A count proven in a stand in proves the hook code, never that the game calls the function; and every path that installs a hook gets its own counted part in the host test, so the cover is by design (the [hooks] section path had none, parts 6 and 8 taking the detour.c and export paths, and only the Wine window test counted it).
Evidence: the T10B3F bisection's run A (DECISIONS.md "2026-11-08 (Fable, the bisection: the example's focus loss and the own hook path's count)", ruling 2): the hook on GAudio::ProcessAudioGameTurn in place for 85.5 seconds with 17 count lines at 0 and the bytes restored equal (05_work/testruns/20261104-122203-bw2hook-logs/20261104-122001.log; 05_work/analysis/fable-review-20261108b/owner-logs-run.txt); the jmp landing on slot stub 0 of a DLL at 0x70B00000 with all 32 stub operands relocated (stub_reloc_read.py, stub-relocs-run.txt); the same [hooks] path counting at 50 per second in the stand in under Wine (05_work/analysis/hook/run-logs/b3-window-test.txt lines 17, 27 and 32 to 35; b3f-window-test.txt the same); the per turn call gated by the game's turn runner 0x5fdce0 before 0x5fd900 and 0x5f8800 reach 0x4d6880 (caller_read.py with capstone over the vault exe, callers-run.txt); the host test's parts 6 and 8 (hooktest.c lines 65 to 66 and 122). The T10B2 control run of card T10B3G-own-hook-count.md is the pair.

### a-zero-at-an-idle-screen-measures-the-game-not-the-hook
Rule: a count of zero at an idle screen (a main menu, a pause screen, a loading screen) measures the game's state at that screen, not the hook; the count test of a hook belongs where the function is known to run (a land that is running its turns for a per turn function, a drawn frame for a draw function), and the checklist says so before the owner's first run. A menu that happened to call the function once is not a promise that it will again: the same build by hash can count there one morning and read 0 a week later. And a control run proves its side only when it runs under the condition the test run had: a control that shares the disturbance (here, both runs minimising) shows that the disturbance is not the build's, and leaves the count to a test where the function must run.
Evidence: the owner's paired runs F and G of 2026-11-10 (DECISIONS.md "2026-11-10 (Fable, runs F and G: not our build; the count test moves into a game; the hook thread closes for the pause)", ruling 1): the T10B2 build that counted 287 calls in 50 seconds at the main menu on 2026-11-02 at 10:15 read 0 over 55.2 seconds on 2026-11-10 with its two files equal to commit c2d2c74's SHA256SUMS.txt and its jmp landing on the same rva 0x2ef0, the current build read 0 beside it, both minimising with the example deleted (confirm_runs_FG.py, 05_work/analysis/fable-review-20261110/owner-logs-run.txt; jmp-landing-run.txt, objdump); five runs with a hook since that morning, all 0, one of them in front for 85.5 seconds (05_work/analysis/fable-review-20261108b/owner-logs-run.txt). Seven owner runs (two on 2026-11-02 and 2026-11-03, three on 2026-11-04, two on 2026-11-10), two cards (T10B3F, T10B3G) and a planned third (T10B3H) were spent on a zero that a 30 second run inside a land would have answered on 2026-11-02; the in-game checklist 08_notes/T10B3-OWNER-INGAME-CHECKLIST.md is that run.

### name-the-window-that-took-the-screen-before-reading-it-as-the-builds-fault

### a-position-sign-cannot-see-a-gap-whose-order-changed
Rule: a sign that pairs functions by their place between two anchors assumes that both builds keep the same order inside the gap. Where the order differs, every row of that gap is wrong together, and nothing about any single row shows it. First, each row's second sign is tried against every other candidate of the same gap: where another candidate passes too, the sign has not chosen, and the row is filed with the rows that have no second sign. Second, the blind test and the holdout report the rows on each side of that cut apart, because a band's figure can be carried by the rows that have a strong check while the rows that have none hide inside it. ### a-ground-in-words-is-an-assertion-make-it-a-claim-and-show-the-reader-the-look-alike
Rule: when a reader must say that something "belongs to this name and not to its siblings", two things are built into the form and neither is left to a sentence. Whatever the script would have to read from the side under test, it reads only in the run that opens the key, so that its answers cannot be used to mark a row unread. A row the reader cannot tell from its look alike gets a mark that says so and is not counted. Without such a mark the form leaves only a guess, a false no, or a reading thrown away.
