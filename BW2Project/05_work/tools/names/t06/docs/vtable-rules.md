# vtable rules for the T06 name transfer (v1.42 against the Mac build)

The rules the scripts in this folder apply, numbered as the cards number them. Rules 1 to 9 are worded in full on BW2Project/08_notes/tasks/T06P-pathing-classes.md, rules 11 to 14 on T06-name-transfer-v1-anchors.md (plan of 2026-10-26, batch 2 rulings of 2026-10-27), rule 15 on the same card (batch 2 ruling of 2026-10-27). This file holds rule 16 in full, written before its code (T06B2-v142-remainder.md item 4), and rule 15 in full, written before its code (T06B3-band.md item 1), and one line on each of the others so a reader has the list in one place.

1. Class names reduced to one form on both sides (MSVC RTTI name and Itanium _ZTV symbol; nested names as Outer::Inner).
2. Template instantiations: skipped and counted in the pilot and batch 1; paired under rule 16 from batch 2.
3. Only the primary vtable (object offset 0) is paired; secondary vtables are counted and skipped.
4. A Mac __cxa_pure_virtual entry names nothing and is counted as pure.
5. The Itanium D1 and D0 destructor pair counts as one slot against MSVC's scalar deleting destructor.
6. Adjacent Mac entries with one function name are an overload group; each PC slot in it gets the shared name, signature not assigned.
7. A name is emitted only when the slot counts are equal after rules 5 and 13 and the RTTI class matches by rule 1.
8. Every name carries a status and a reason.
9. Part-time God's vtable address is compared with the census address, with no weight.
11. Folded bodies: a PC address reached through slots with different Mac names keeps every name, status "folded, N names".
12. The PC _purecall stub names nothing; pure slots must sit at the same positions on both sides, otherwise the class is skipped.
13. Pure destructor pair: two adjacent Mac pure entries count as one slot under three conditions.
14. Two census vftables at object offset 0 for one class: skipped. From batch 2 only slotted records count, after the test of item 3 of T06B2 (a 0 slot record holding no pointer into .text is set aside).
15. The band: in a class derived from Object the PC order of Object's slots is the Mac order with two changes (the moved method and the MSVC overload order), applied only after band_test.py prints HOLDS; in full below.
17. A method present in one build only is dropped from that build's vtable before the counts are compared, under the conditions below, applied only after rule17_test.py prints HOLDS; in full below (T06B4).
18. Trailing Mac primary slots that override a method of a non-primary base are dropped before the counts are compared and named through the PC secondary vftable of that base, applied only after rule18.py prints HOLDS; in full below (T06B5).

## Rule 16, template instantiations (T06B2, 2026-10-27)

- The PC name is the MSVC RTTI type name of the census vftable record (typedesc, for example `.?AV?$GPacketCreator@VGPacketAftertouch@@@@`), demangled by llvm-undname (the version is printed by pair.py) as the type descriptor `??_R0<typedesc without its first character>@8`. The Mac name is the class part of the _ZTV symbol demangled by c++filt, as for every other class.
- Both names are reduced the same way: the words `class ` and `struct ` are dropped wherever they stand (MSVC writes them before every class argument, the Mac never does); every space next to `,`, `<`, `>`, `*` and `&` is removed, so `A<B *, C>` and `A<B*,C>` and `A<B<C> >` and `A<B<C>>` reduce alike; runs of spaces become one. Nothing else changes: namespaces stay (rule 1, `std::vector`), type names stay as each compiler spells them (`unsigned int` on both sides stays `unsigned int`), integer arguments stay as printed, and no other word (such as `enum `) is dropped.
- A template class pairs only when its reduced PC name equals the reduced name of exactly one Mac class and the slot counts are equal after rules 5 and 13; then rules 3 to 14 apply to it as to any class, and its rows carry the reduced name as the class.
- A template whose reduced name matches no Mac class, or more than one, is skipped with the reason "template" and counted under "rule 16, no Mac symbol"; pair.py prints one example of each spelling per template family it cannot pair, and the report lists the families as documented skips.
- The std and runtime templates are counted apart in the output but their names count like any other.

## Rule 15, the band (T06B3, 2026-10-28; the card's words, BW2Project/08_notes/tasks/T06B3-band.md)

In a class derived from Object (its census bases include Object, or it is Object), the PC order of Object's slots is the Mac order with two changes, both read from the Mac order alone:
- First, the moved method: Object::GetImpressiveValue() with no arguments, Mac slot 581, sits at PC slot 470, and every Mac slot 470 to 580 sits at PC slot 471 to 581 (band_test.py part b of T06B2: 120 of 120 classes agree at +1 at every band slot except the overload slots below, and 120 of 120 for the moved method; from 440 to 469 and from 582 to 606 every class agrees at offset 0).
- Second, the overload order: where a method name has overloads declared apart on the Mac, MSVC places every overload of that name together at the position of the first declared one, the last declared first. At Mac slots 509 to 512 (NetworkUnfriendlyStartLockedApply(MapCoords*), NetworkUnfriendlyEndLockedApply(MapCoords*), NetworkUnfriendlyStartLockedApply(Object*), NetworkUnfriendlyEndLockedApply(Object*)) that places them at PC slots 511, 513, 510 and 512 (band_test.py part f; the verifier's slots509-513.txt reads the same grouping in the eight overriding classes).
- Adjacent overload groups (rule 6: adjacent Mac entries with one function name) are named by the shared name with no signature, as before; their internal order is not claimed by this rule. The executor's part f reversed them and found Villager disagreeing at 485 inside the IsTouching group (483 to 485), which rule 6 names IsTouching whichever entry sits where.
- Rows named through this rule carry the reason "slot pairing, rule 15 (band)" and the status "claimed, T06B3 (band)". The rule applies to no class that is not derived from Object and to no slot outside Object's own slots.

The agreement clause (written by the Fable reviewer, 2026-10-28, DECISIONS.md "2026-10-28 (Fable, the band test, batch 4)"; the reviewer's one edit of this file, the rest is the executor's): in the test of this rule, a PC slot whose entry is a body the linker shares across classes (an address that sits at slots of other classes under other Mac method names, the rule 11 shape) agrees with the Mac entry the rule places there whenever that Mac entry's body is byte identical, addresses aside, to the body of the Mac symbol that the PC entry's owner class carries at the same method. There is nothing to tell apart: the PC build folded two identical bodies into one address, and the Mac build kept two identical bodies under two symbols. This is rule 11's folding applied to the slot comparison, not to the naming; the names of such a row are still written as rule 11 writes them. The test prints every slot it settles by this clause with the class, the PC address and the two Mac symbols, so a reader sees how often it was used; the slots it may settle are exactly those where the plain owner reading disagrees, and in batch 3 those were three (SiegeWeaponFlag at PC slots 449, 517 and 557, b3-band-test.txt). A slot where the Mac bodies differ, or where the PC entry is not shared, is a disagreement and the test prints FAILS as before. Under this clause both readings of "at the level the names are written" (the owner reading of band_test.py and the T06B2 part b reading) hold on all 120 classes (the T06B3 verification, band-mine3-run.txt and bodies-mine-run.txt).

Not claimed (recorded from T06B2, BW2Project/05_work/analysis/t06/run-logs/b2-band-test.txt part f): the overload order, applied to adjacent groups as well, would reverse two adjacent groups of Object's own slots, Mac 363 to 364 and Mac 483 to 485. This rule does not reverse them: their internal order is left to rule 6, and 363 to 364 lies outside the band, where nothing changes in T06B3.

## Rule 17, a method present in one build only (T06B4, 2026-10-28; the card's words, BW2Project/08_notes/tasks/T06B4-band-names.md, written before its code)

A method present in one build only is dropped from that build's vtable before the counts are compared, when the counts differ by exactly one, the method has a body in that build's text and the other build has no string and no symbol of it, and its slot (chosen by the method's own _ZTV position in each class, never by the deletion test alone) is among the deletions that make the class agree with every reference class (the primary base and the classes based on it).
- In T06B4 it applies to one method, GiveMouseActionOnCmdQuit, Mac only: two Mac bodies (MenuPane::GiveMouseActionOnCmdQuit at 0xc03458 and MenuPaneCallback::GiveMouseActionOnCmdQuit at 0xc02db8), 71 _ZTV records, 0 direct and 409 indirect callers, 0 strings in white.exe against 2, 2 and 3 in the Mac binary (BW2Project/05_work/analysis/t06/run-logs/b3-menu-cmdquit.txt, menu_cmdquit.py; the T06B3 verifier's menu-mine-run.txt), in MenuPane, MenuPaneCallback and the classes derived from them.
- The slot is the position of the method's own _ZTV entry in the class's Mac list after rules 4 to 6, never a slot the deletion test alone picks: for MenuPane the deletion of GiveMouseAction at slot 10 also agrees with the reference classes (the T06B3 verifier's menu-mine-run.txt), and slot 11, the method's own, is the one deleted.
- The test, before any name (rule17_test.py): for MenuPane, MenuPaneCallback and every class derived from either that carries the method, the method's slot is deleted at its own position; the class pairs when then the Mac count equals the PC count, the deletion is among those that agree with every reference class (the deletion test of unequal_report.py, T06B2), and the Mac pure positions equal the PC _purecall stub positions (rule 12). HOLDS when 63 classes pair and the 6 that do not are MenuPaneCallback_Confirmation, _EndLevel, _LoadProfile, _LoadSave, _NameEntry and _SelectProfile (b3-menu-cmdquit.txt); FAILS with the list otherwise.
- Rows named through this rule carry the reason "slot pairing, rule 17 (Mac only slot deleted)" and the status "claimed, T06B4 (rule 17)". A class that does not pair stays unequal ("slot counts differ"). The 5 MenuManager classes and the 12 secondary overrider classes of unequal_report.py stay unequal in T06B4 (no rule for them yet).

### Rule 17's reference clause (T06B5; the card's words, BW2Project/08_notes/tasks/T06B5-remaining-classes.md Goal (ii), written before its code)

When the primary base of a class has no census vftable, the reference classes of the deletion test are the nearest base in the RTTI chain that has one and the classes already paired under rule 17 from it; the deletion at the method's own _ZTV position must agree with all of them.
- The primary base is the first base of the class's census bases list (the list after the class itself); it "has no census vftable" when no census vftable record carries its RTTI name. The nearest base that has one is the first base after it in the same list that has one slotted census primary and a Mac vtable (unequal_report.tables), so that the deletion test can read it.
- The classes already paired under rule 17 from it are the classes of the batch 4 test (rule17_test.py, GiveMouseActionOnCmdQuit) that pair there and have that base among their census bases. The nearest base itself is a reference class whether or not it pairs under rule 17.
- The deletion test is unequal_report.py's, unchanged: at every other slot both sides say "same entry as the reference" or both say "different", a reference one slot longer than its PC list being shifted at the same position. The method's own slot (its _ZTV position after rules 4 to 6) must be among the deletions that agree; the counts must then be equal and the Mac pure positions equal the PC stub positions (rule 12), as for every rule 17 class.
- The test set is the classes of the batch 4 test that do not pair there and whose primary base has no census vftable. The test (rule17_test.py --reference, one attempt) prints the reference classes and, per class, the slot deleted or the reason; HOLDS when the test set is exactly MenuPaneCallback_Confirmation, _EndLevel, _LoadProfile, _LoadSave, _NameEntry and _SelectProfile and all 6 pair; FAILS otherwise, and then none of the 6 is named and they stay unequal ("slot counts differ").
- Rows named through the clause carry the reason "slot pairing, rule 17 (Mac only slot deleted; reference clause)" and, when only these classes reach them, the status "claimed, T06B5 (rule 17)".

### Rule 17 with the BotG bridge, the MenuManager classes (T06B5; the card's words, Goal (iii), written before its code)

The 5 MenuManager classes (MenuManager Mac 21, PC 20; MenuManagerToolbar, MenuManagerWrapper, MenuManager_ToolbarImpl and MenuManager_WrapperImpl Mac 22, PC 21) were the accepted limit of 2026-10-28. T09B2's alignment of the v1.42 MenuManager vtables against the BotG ones (BW2Project/05_work/analysis/t09/run-logs/b2-menumanager-bridge.txt; the verifier's BW2Project/05_work/analysis/t09b2-verification/out/v-bridge.txt) gives the one BotG slot with no v1.42 counterpart as BotG slot 20, MenuManager::UpdateTooltips, in MenuManager, MenuManager_ToolbarImpl and MenuManager_WrapperImpl, and leaves the insert unlocated in MenuManagerToolbar and MenuManagerWrapper, whose gaps hold MenuManagerToolbar::UpdateTooltips and MenuManager::UpdateTooltips. So the method v1.42 lacks is UpdateTooltips in all five. The bridge chooses the method, never the slot: the slot dropped is UpdateTooltips's own position in each class's Mac list after rules 4 to 6, read from the _ZTV, never the BotG slot number, and rule 17's own conditions and test decide every one of the five, the two unlocated classes included.
- The conditions, as for GiveMouseActionOnCmdQuit (menu_cmdquit.py's method): the counts differ by exactly one; a Mac body, every defined symbol in __text whose name holds UpdateTooltips, with its address, size and calls read by capstone; no PC string, no printable run of 6 or more bytes in white.exe holding "UpdateTooltips" (the Mac binary searched the same way as a control; runs holding "Tooltip" are printed as an aid, not a condition); no PC symbol, white.exe carries no symbol table, which the test prints.
- The deletion test with rule 17's reference classes (the primary base and the classes whose primary base it is); the counts then equal and the Mac pure positions equal to the PC stub positions.
- The test set: MenuManager and every class with MenuManager among its census bases whose Mac list carries a method named UpdateTooltips. The test (rule17_test.py --bridge, one attempt) prints the conditions, per class the slot deleted or the reason, and the classes outside the test set whose Mac list carries the method; HOLDS when the test set is exactly the 5 MenuManager classes, all 5 pair and the conditions hold; FAILS otherwise, and then none of the 5 is named.
- The names are the Mac names at the remaining slots, slot for slot; nothing is named by position against BotG. Rows carry the reason "slot pairing, rule 17 (Mac only slot deleted; BotG bridge)" and, when only these classes reach them, the status "claimed, T06B5 (rule 17)".

## Rule 18, secondary overriders (T06B5; the card's words, Goal (i), and DECISIONS.md "2026-10-28 (Fable, T06 batch 4 sign-off, license, T08 and T09)", written before its code)

A trailing Mac primary slot whose symbol overrides a method declared in a non-primary base (read from that base's own _ZTV) is dropped from the Mac primary list before the counts are compared; the dropped methods are named only through the PC secondary vftable of that base in the class (rule 3), slot for slot against the base's Mac vtable. The Itanium ABI appends such an overrider to the primary vtable; MSVC keeps it in the secondary vftable only.
- The extra slots are the trailing (Mac count less PC count) slots of the class's Mac primary list after rules 4 to 6.
- A slot overrides a method declared in a non-primary base B, read from B's own _ZTV, when: the class's Mac _ZTV holds a secondary group with the non-virtual thunk (__ZThn<offset>_) whose target is the slot's symbol; that group matches B's own _ZTV primary entries slot for slot (the same number of raw entries, and at every position B's entry is pure, or both are destructors, or both carry the same method name and parameter list); B is a base of the class in its census bases list; and B is not a primary base, its member displacement in the class (mdisp of its base class descriptor, read from white.exe's RTTI through the census record's complete object locator) not being 0. Where several bases of the list match one group, the first in the list whose mdisp is not 0 is taken and the others are printed; a base at mdisp 0 is the primary base and never the one a secondary overrider overrides.
- The PC census holds a secondary vftable for that base in the class when a census vftable record of the class has col_offset equal to that mdisp.
- After the drop the counts are equal, and the Mac pure positions equal the PC stub positions (rule 12).
- The test, per class (rule18.py, one attempt over the 12 classes CPUSkinnedSortedHairSlice, HairySkinImpl, HairySkinImplCPU, HairySkinImplVertexShader, LH3DHairySkinMaterialMorphingTextureMethod, LH3DTextureNonUniformMorpher, LHSkin, SortedHairSlice, VertexShaderSkinnedSortedHairSlice, CreatureFight, CreatureLearningMatrix and CreatureRoles, read from class-counts.tsv as the classes whose secondary category unequal_report.py prints): every extra slot is such an override, the PC census holds the secondary vftable, and after the drop the counts are equal and the pure positions agree. HOLDS when all 12 hold; FAILS otherwise, and then none of the 12 is named and they stay unequal.
- Naming: the remaining primary slots pair slot for slot as for any class. A dropped method sits at position q of its group after rules 4 and 5 (a destructor thunk pair counts as one slot); it names the PC address at slot q of the base's secondary vftable when the group's slot count equals that vftable's slot count, and nothing otherwise (counted and printed). Its row's slot column holds q, the slot in the secondary vftable, and its reason says so: "secondary vftable of <base> at offset <mdisp>, slot <q>, rule 18 (secondary overrider)". The primary slots carry "slot pairing, rule 18 (secondary overriders dropped)". A one name row only rule 18 classes reach gets the status "claimed, T06B5 (rule 18)".

### T06B5 in the tables
A row any class of an earlier batch also reaches keeps that batch's status and reason unless rule 11 folds it; the T06B5 classes then only add to its reached_by, or to its class and slot lists, or add a name through rule 11 (the allowance of 2026-10-28, counted by diff_batch1.py --b4 and --b5); a one name row that gains a second name through rule 11 becomes a folded row with rule 11's status and reason, as every folded row is, because a single name status cannot carry two names (0x4bedd0, T06B6; Fable ruling 2026-11-01). The blind test of ruling 3 (DECISIONS.md 2026-10-30) binds methods other than the vtable method; rule 18 and the two rule 17 readings are rules inside the vtable method, so their gate is their own HOLDS test and the verifier's holdout.
